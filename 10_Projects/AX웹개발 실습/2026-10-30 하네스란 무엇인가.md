# 하네스란 무엇인가

> AI 개발에서 하네스(harness)는 모델이 자료를 읽고 도구를 사용하면서 여러 단계의 작업을 이어가도록 관리하는 실행 체계다.

## 이 글에서 말하는 하네스

하네스라는 말은 분야에 따라 다르게 쓰인다. 전기·전자에서는 배선을 묶은 구조를, 소프트웨어 테스트에서는 시험 대상에 입력을 주고 결과를 확인하는 테스트 장치를 가리키기도 한다.

이 글은 **AI 에이전트 하네스(agent harness)**에 관한 설명이다. 특정 회사의 제품 이름 하나를 뜻하는 것이 아니라, AI 모델 주변에서 작업 실행을 관리하는 소프트웨어 계층을 가리킨다.

VS Code 공식 문서는 하네스를 에이전트 세션을 실행하는 소프트웨어 계층으로 설명한다. 모델에 문맥과 도구를 연결하고, 작업이 진행되는 동안 반복 실행과 세션 상태를 관리한다. [VS Code 공식 설명](https://code.visualstudio.com/docs/agents/concepts/agent-harnesses)

## 모델과 하네스는 무엇이 다를까?

모델은 전달받은 내용을 바탕으로 답변하거나 다음에 사용할 도구를 요청한다. 하네스는 그 요청을 실제 작업 과정으로 이어준다.

예를 들어 “이 문서를 읽고 HTML을 만들어 줘”라는 요청에는 글을 생성하는 것 외에도 파일 읽기, 파일 저장, 명령 실행, 결과 확인이 필요할 수 있다. 하네스는 이 과정에서 모델에 어떤 정보를 전달할지, 요청한 도구를 실행해도 되는지, 실행 결과를 어떻게 돌려줄지 관리한다.

| 구성요소 | 맡는 역할 |
| --- | --- |
| AI 모델 | 내용을 이해하고 답변하거나 다음 행동을 요청한다. |
| 하네스 | 모델 호출, 도구 실행, 권한 확인, 작업 상태 관리를 연결한다. |
| 도구 | 파일 읽기·쓰기, 검색, 명령 실행 등 구체적인 기능을 수행한다. |
| 실행 환경 | 파일과 도구가 실제로 존재하고 실행되는 장소다. 내 PC나 원격 환경 등이 해당한다. |

실행 환경과 하네스는 서로 관련되어 있지만 같은 개념은 아니다. 하네스가 작업을 조율하고, 환경은 그 작업이 수행되는 장소를 제공한다. [VS Code 공식 설명](https://code.visualstudio.com/docs/agents/concepts/agent-harnesses)

## 하네스가 보통 관리하는 것

제품마다 범위와 구현은 다르지만, 다음과 같은 기능이 포함될 수 있다.

- **문맥 준비:** 사용자 요청, 이전 대화, 필요한 자료와 작업 지침을 모델에 전달한다.
- **도구 연결:** 모델이 요청한 기능을 호출하고 결과를 다시 전달한다.
- **권한 적용:** 도구 실행에 필요한 승인과 접근 범위를 확인한다.
- **반복 실행:** 결과를 보고 다음 행동을 선택하는 과정을 이어간다.
- **상태와 기록:** 진행 상황, 메시지, 도구 결과 등을 관리한다.
- **종료와 복구:** 작업을 마칠지, 추가 입력이 필요한지, 실패 후 어떻게 이어갈지 처리한다.

이런 역할을 묶어 **에이전트 루프(agent loop)**를 운영한다고 설명할 수 있다. 실제 책임을 하네스와 별도 런타임 사이에 어떻게 나누는지는 구현에 따라 달라진다. [Cloudflare 공식 설명](https://developers.cloudflare.com/agents/harnesses/)

## 한 번의 요청이 작업으로 이어지는 흐름

다음은 개념을 이해하기 위한 간단한 예다.

```text
사용자: “AX 폴더에 설명 문서를 만들어 줘.”
    ↓
하네스가 요청·작업 규칙·사용 가능한 도구를 모델에 전달
    ↓
모델이 필요한 파일 읽기를 요청
    ↓
권한 확인 후 도구 실행 → 결과를 모델에 전달
    ↓
모델이 내용을 구성하고 파일 저장을 요청
    ↓
도구로 파일 저장 → 결과 확인
    ↓
필요하면 수정하거나 추가 확인 → 완료 보고
```

핵심은 **모델의 판단과 실제 실행 사이에 관리 과정이 있다는 것**이다. 하네스가 있다고 해서 모든 도구 사용이 허용되거나 모든 작업이 자동으로 완료되는 것은 아니다.

## 오래 걸리는 작업에서 중요한 이유

AI가 큰 프로그램을 만들 때는 한 번의 응답으로 끝나지 않는 경우가 많다. 작업 중간에 대화 길이 제한에 도달하거나 세션이 바뀌면, 앞에서 무엇을 했고 무엇이 남았는지 이어받을 방법이 필요하다.

Anthropic은 장기 실행 에이전트 실험에서 초기 환경 준비, 단계별 기능 구현, 진행 기록, 테스트와 인수인계 자료를 활용하는 방식을 소개했다. 강력한 모델을 단순히 반복 호출하는 것만으로는 긴 작업의 일관된 진행을 보장하기 어렵다는 문제를 다룬 사례다. [Anthropic 공식 사례](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

따라서 좋은 하네스를 설계한다는 것은 “계속 실행하기”뿐 아니라 **다음 작업에 필요한 상태를 남기고, 완료 여부를 확인할 수 있게 만드는 것**과도 관련된다.

## MCP·CLI·크론잡·작업 규칙과 비교하기

| 용어 | 핵심 질문 | 역할 |
| --- | --- | --- |
| 하네스 | AI가 작업을 어떤 과정으로 이어갈까? | 모델·도구·문맥·상태를 연결하고 반복 실행을 관리 |
| MCP | AI와 외부 기능을 어떤 공통 규칙으로 연결할까? | 외부 도구·자료와 통신하는 표준 |
| CLI | 프로그램에 어떤 방식으로 명령을 내릴까? | 글자 명령으로 프로그램을 사용하는 인터페이스 |
| 크론잡·작업 스케줄러 | 언제 실행할까? | 정해진 시점이나 주기에 작업 실행 |
| 프롬프트·작업 규칙 | 무엇을 어떤 기준으로 할까? | 목표, 설명 방식, 형식과 행동 기준을 안내 |
| 샌드박스 | 실행과 접근을 어느 범위로 제한할까? | 코드·도구가 실행되는 격리·제한 환경 |

이들은 함께 사용할 수 있다. 예를 들어 하네스가 MCP 도구나 CLI 명령을 이용하도록 구성할 수 있고, 스케줄러가 에이전트 실행을 시작하게 할 수도 있다. 다만 하네스가 반드시 MCP나 예약 기능을 포함해야 하는 것은 아니다.

## 내가 진행한 AX 작업에 대입해 보기

### 문서 작성

`AGENTS.md`, `CLAUDE.md`, `작업규칙.md`는 작성자·태그·읽음 여부 같은 기준을 담는다. 이런 파일은 하네스가 모델에 제공할 수 있는 **작업 지침**이며, 파일 하나가 하네스 전체인 것은 아니다.

### 포트폴리오 배포

파일을 확인하고, 배포 명령을 실행하고, 실행 결과와 웹페이지 응답을 확인하는 과정을 AI와 함께 진행했다. 이 사례는 모델의 판단, 도구 실행, 결과 확인이 이어지는 작업 흐름을 이해하는 데 도움이 된다.

### 매시간 GitHub 업로드

현재 등록한 자동 업로드는 Windows 작업 스케줄러가 PowerShell 스크립트를 실행하는 방식이다. 매번 AI 모델을 호출해 판단하는 구조로 만든 것은 아니므로, 이 자동화를 곧바로 AI 에이전트 하네스라고 부르기는 어렵다.

## 하네스를 만들거나 선택할 때 생각할 점

- 필요한 파일과 도구만 접근하도록 범위를 정했는가?
- 중요한 변경이나 외부 전송에 어떤 승인 규칙을 적용하는가?
- 실패했을 때 원인을 확인하고 이어서 작업할 기록이 남는가?
- “끝났다”는 판단을 실제 파일·테스트·실행 결과로 확인하는가?

특히 볼트에는 개인 이력과 인증 관련 파일도 있을 수 있다. 모델이 유용하게 작업하도록 연결하는 것과, 모든 파일을 자유롭게 읽거나 외부로 보내도록 허용하는 것은 구분해야 한다.

## 한 문장 정리

**하네스는 AI 모델을 도구·문맥·권한·작업 기록과 연결해, 여러 단계의 일을 실제로 수행하도록 관리하는 실행 체계다.**
